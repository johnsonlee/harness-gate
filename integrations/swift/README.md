# Harness Swift rules and native build plugin

Swift 5.10+, Xcode 15.4+, macOS 13+ host; supports SwiftPM targets and native Xcode iOS targets. The executable runs on the build host, not on the device. No Node.js or harness CLI is required.

## SwiftPM consumer

Install this directory as a Swift package dependency. For a checkout/submodule of the full harness repository:

```swift
// swift-tools-version: 5.10
import PackageDescription
let package = Package(
    name: "Example",
    dependencies: [.package(name: "HarnessSwift", path: "vendor/harness/integrations/swift")],
    targets: [
        .target(name: "App", plugins: [
            .plugin(name: "HarnessBuildPlugin", package: "HarnessSwift")
        ])
    ]
)
```

Attach the plugin to every target requiring enforcement, including test targets if desired. Pin the vendored repository/submodule revision. SwiftPM cannot install a package from a remote repository subdirectory: a future remote Swift package release must publish this directory as its repository root; then use an exact package version and commit `Package.resolved`.

Add `harness-swift.json` next to the consumer's `Package.swift`:

```json
{
  "version": 1,
  "targets": {
    "App": {
      "forbiddenImports": ["Storage"],
      "allowedImports": ["Foundation", "Domain", "UIKit"]
    }
  }
}
```

`forbiddenImports` is required (use `[]` to explicitly permit all imports). `allowedImports` is optional; when present it is an exhaustive module allowlist, including SDK modules. Matching uses the root module (`import struct Storage.Item` checks `Storage`). A forbidden import always fails, even if also allowed. An absent configuration or target entry, unsupported version, unreadable source, or malformed configuration fails the build.

Run the ordinary `swift build` or `swift test`. Checks run as native build commands, with source files and configuration as declared inputs. Source/config changes invalidate the result; SwiftPM handles plugin/tool rebuilding. The JSON report is a declared build output in the plugin work directory (`harness-report.json`), never a file in consumer source control.

## Native Xcode iOS target

1. Add this directory as a local package in the Xcode project (or use a separately published, pinned Swift package distribution).
2. In each target's **Build Phases → Run Build Tool Plug-ins**, add `HarnessBuildPlugin`.
3. Add `harness-swift.json` alongside `.xcodeproj`. Keys under `targets` match target display names exactly.
4. Build normally in Xcode or with `xcodebuild`; plugin diagnostics and failures participate in the native build.

Xcode may request trust for the plugin. CI should establish trust for the pinned package using the organization's standard mechanism. The isolated integration test uses `-skipPackagePluginValidation` only for its generated local fixture.

## Reuse the rules or checker

Import the `HarnessRules` library and call `SwiftRules.check(source:file:rules:)`. Or run the executable directly:

```sh
swift run --package-path vendor/harness/integrations/swift harness-swift-lint \
  --root "$PWD" --config "$PWD/harness-swift.json" --target App \
  --source "$PWD/Sources/App/App.swift" --report "$PWD/.build/harness-report.json"
```

Repeat `--source` for every Swift input. JSON stdout/report contains `version: 1`, `checkId: "swift:<target>"`, `status: pass|fail|error`, and findings with rule ID, severity, message, repository-relative file, and one-based line. Diagnostics go to stderr. Exit codes: 0 pass, 1 rule violations, 2 configuration/execution failure. Rules: `swift/forbidden-import`, `swift/module-boundary`.

## Coverage and limits

This is a lexical import boundary checker, not a compiler type/AST analysis or a complete dependency graph. It handles scoped and attributed imports, semicolon-separated imports, nested comments, ordinary/raw/multiline strings, and extended regex literals. All conditional-compilation branches are checked, deliberately independent of the build destination. It does not inspect Objective-C imports, linker settings, reflection, transitive imports, or source generated by other build plugins. A successful result proves only the configured rules over supplied Swift inputs. Compiler syntax errors remain the compiler's responsibility. Existing SwiftLint/other tools can run alongside this plugin.

## Verification

```sh
swift test --package-path integrations/swift
python3 integrations/swift/scripts/integration.py
```

The integration script copies the distribution to a detached temporary directory, installs it into independent SwiftPM and native Xcode iOS framework consumers, and checks native build success, rule failure, config/source invalidation, and missing-config failure. It uses the iOS Simulator SDK without launching a simulator or requiring signing. Xcode checks are explicitly skipped on non-Xcode hosts or with `HARNESS_SKIP_XCODE=1`.
